# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Carta — a free daily trivia game ("Daily Atlas Trivia") by Okapia Games, served entirely from a single Cloudflare Worker. No framework, no build tooling beyond a one-file inliner. Live at carta.okapiagames.com.

## Commands

```bash
npm install                          # installs wrangler (only dependency)
npm run dev                          # build + wrangler dev → http://localhost:8787
npm run build                        # node build.js → inlines src/game.html into dist/worker.js
npm run deploy                       # build + wrangler deploy dist/worker.js
npx wrangler secret put ANTHROPIC_API_KEY      # required to generate questions locally
npx wrangler secret put GOOGLE_TRANSLATE_KEY   # optional, enables translated questions
./scripts/health-check.sh            # live-site + deployment + KV/R2 health snapshot
```

There is no test suite or linter configured — verify changes via `npm run dev` and manual checks against the endpoints below.

Deploys to production happen automatically via `.github/workflows/deploy.yml` on every push to `main` (`npm ci && npm run deploy`, using `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` repo secrets). There is no separate CD command to run manually — `git push origin main` is the deploy trigger. See DEPLOY.md for full setup and cost details.

## Architecture

**Build step is a literal string inline, not a bundler.** `build.js` reads `src/game.html`, escapes backticks/`${}`, and substitutes it into the `` `__GAME_HTML__` `` placeholder in `src/worker.js`, producing the single deployable file `dist/worker.js`. Always edit `src/worker.js` and `src/game.html` — never `dist/worker.js` directly (it's regenerated and gitignored).

**Two files hold all logic:**
- `src/worker.js` — Cloudflare Worker: router, daily question generation, scoring, sharing, translations. Bindings: `TRIVIA_KV` (KV namespace), `POSTCARDS` (R2 bucket), secrets `ANTHROPIC_API_KEY` / `GOOGLE_TRANSLATE_KEY`.
- `src/game.html` — entire frontend (markup + CSS + vanilla JS) as one string, served directly by the Worker at `/`.

**Two editions, one codebase.** `carta.okapiagames.com` (global) and `cartain.okapiagames.com` ("Carta.In" wordmark — Indian subcontinent only) are the same Worker deployment, branching on request hostname rather than being separate repos/deployments — `siteOf(request)` in worker.js returns `'in'` or `'global'`, threaded through `getDailyQuestions`/`generateDailyBatch`/the `/api/questions`, `/api/score`, `/api/leaderboard` handlers. The domain is spelled `cartain` (one DNS label) rather than `carta.in` (two labels, closer to the wordmark) because Cloudflare's free Universal SSL certificate only covers the apex domain plus one level of wildcard subdomain — a two-label hostname needs the paid Advanced Certificate Manager or Total TLS enabled. Every date-scoped KV key gets prefixed via `siteKey(site, key)` (`questions:`, `lock:`, `used_topics`, `scores:`, `player_count:`, `circuit_breaker_alerted:`) so the two editions never collide on the same key for the same date — they share the single `TRIVIA_KV` binding and `POSTCARDS` bucket, no separate namespace/bucket provisioned. `catmembers:*` (Wikipedia category-member cache) and `about_translations:v1` are deliberately left unprefixed/shared, since that data is identical across editions. Client-side, `game.html` detects the edition via `IS_IN_SITE = location.hostname.startsWith('cartain.')` and derives `BRAND` (`'Carta'` vs `'Carta.In'`) from it — used for the wordmark (header, title screen, About tab, postcard canvas text) and the indigo `body.theme-in` CSS override (just re-points the `--p-*` primitives block — including `--p-gold`, which is repointed to a vivid indigo rather than an actual gold, since `--gold`/`--accent`/`--border-gold` all derive from it and that's what makes indigo the dominant accent color rather than confining it to body text via `--p-ink`; the semantic CSS layer picks it up everywhere except `generatePostcard()`'s canvas code, which carries its own literal hex palette independent of CSS and needs a parallel `P` branch kept manually in sync).

**Daily question generation** (`getDailyQuestions` → `generateDailyBatch` in worker.js): normally triggered by the first request after UTC midnight, but for the `in` edition it's also pre-warmed proactively — a Cron Trigger (`[triggers]` in `wrangler.toml`, `"0 0 * * *"`) fires the `scheduled` handler at UTC midnight, which calls `getDailyQuestions(env, 'in')` in the background (`ctx.waitUntil`) so the first real India visitor of the day never eats generation latency. The `global` edition is still lazy/on-demand. Either path, the Worker sources 10 real Wikipedia articles and generates all 10 questions in a single Anthropic API call (`claude-haiku-4-5-20251001`, `max_tokens: 4000`), then caches the result. `TOPIC_SLOTS` is 8 accessible (4 History + 4 Geography) + 2 challenging (1 + 1) — weighted further toward easy (previously 6/4) after continued player feedback that the set was too hard. Sourcing (`pickArticlesForSlots` → `pickArticleForSlot`) draws from `CATEGORY_POOL` — a curated, weighted list of Wikipedia categories per region (South Asia, Africa, MENA, SE Asia, etc.) that deliberately overweights non-Western history/geography to correct for Wikipedia's own coverage bias; weights are an intentional editorial choice, not a bug, and shouldn't be casually rebalanced. Each category can also be tagged `broad: true` (a widely-recognized umbrella, e.g. "Mughal Empire", vs. a niche one, e.g. "Bengal Sultanate") — accessible slots prefer `broad` categories, challenging slots draw from the full pool unchanged. Category member lists are cached in KV (`catmembers:{Category_Name}`, 7 days) since they change slowly. Cross-day repeats are avoided via `used_topics` in KV (last 140 titles, 15-day TTL) — Layer 3 dedup falls back to the full unfiltered list rather than ever failing generation. The `cartain` edition passes `allowedRegions: ['South Asia']` (via `SITE_REGIONS`) through this whole pipeline, filtering `CATEGORY_POOL` down to its 19 South Asia entries — including the random-article fallback path (`fetchRandomArticleFromRegions`, used instead of the global `fetchRandomArticle` whenever `allowedRegions` is set), so the region restriction is airtight rather than best-effort.

The 10 articles are assembled into one prompt (the Quizzard persona + a `DAILY_THREADS` rotating theme seeded by date + all 10 article summaries + slot/difficulty descriptions + question-craft/answer-option/explanation/accuracy/content-tone rules) and sent as a single batch call so the model can't generate duplicate themes across questions. Known real limit, not fully solved: a `broad` category name doesn't guarantee an individual member article is famous (Wikipedia's category API doesn't expose article-level "fame"), so `ACCESSIBLE_DIFFICULTY` explicitly tells the model to pivot to whatever well-known thing the article's own summary mentions rather than requiring the sourced article itself to be well-known — this is a prompt-level backstop, unverified against live Haiku output since there's no `ANTHROPIC_API_KEY` available for local testing in this environment. `CONTENT_TONE_RULES` tells the model not to center a question on mass atrocities/tragedies (added after one surfaced live during testing) — also prompt-level, not a hard filter.

`isValidQuestion` + `hasAnswerLeak` filter the response; unless all 10 survive, the whole sourcing+generation attempt is retried, up to 15 times, before failing (previously it accepted 8/10 as a pass, which meant players consistently saw 8- or 9-question games with no visibility into why — each rejected attempt now logs a `console.warn` with the shortfall count, visible via `wrangler tail`). Results are cached in KV under `questions:YYYY-MM-DD` (also storing the day's `thread`) with a TTL through the next midnight + 2h buffer, so every player that day sees the identical question set (this is the point — it makes scores comparable). A KV-based lock (`lock:YYYY-MM-DD`, 240s TTL — raised alongside the 15-attempt retry so a slow generation can't outlive its own lock) prevents duplicate generation when multiple requests race the cache miss; losers poll for up to 45s.

**Translations** are generated once per day alongside questions (`translateQuestions`, Google Cloud Translation API) for `TRANSLATE_LANGS = ['ta','hi','bn','kn','ja']`, and separately for static UI strings (`getAboutTranslations`, cached 30 days under `about_translations:v1`). Both no-op gracefully (frontend falls back to English) if `GOOGLE_TRANSLATE_KEY` isn't set.

**Storage split — KV vs R2 — is deliberate, not incidental:** KV holds daily questions, translations, and leaderboard scores (eventual consistency is fine there). R2 holds shared postcard images specifically because it's strongly consistent — KV's eventual consistency caused WhatsApp/Twitter link-preview crawlers to 404 on freshly-shared images (see DEPLOY.md).

**Circuit breaker:** `/api/questions` counts cache-miss invocations per day in KV (`player_count:YYYY-MM-DD`) and returns 503 past 50,000/day, logging once via a separate `circuit_breaker_alerted` key to avoid log spam.

**Edge caching:** the `edgeCached()` helper wraps handlers with Cloudflare's `caches.default`, setting `s-maxage` per route (`/` and `/api/questions`: 300s, `/api/about`: 3600s, `/api/leaderboard`: 60s) so the circuit breaker and KV only see traffic on cache misses.

**Routes** (all in the single `fetch` handler in worker.js): `/` (game HTML — served with a targeted `<title>`/`og:title` string-replace when `siteOf(request) === 'in'`, since these live in the static HTML head and matter for link previews), `/og.png` (static OG image, shared by both editions), `/api/questions` GET, `/api/score` POST (server recomputes score from submitted `results` array rather than trusting a client-sent score, to prevent leaderboard spoofing), `/api/about` GET, `/api/leaderboard?date=` GET, `/api/share` POST (uploads postcard PNG to R2, returns `/share/:id`), `/img/:id.png` (serves stored postcard).

**Postcards** are generated client-side in `game.html` via `<canvas>` (`generatePostcard`) — no server-side image rendering. Sharing to WhatsApp/Twitter needs a real hosted image for link previews, hence the R2 upload + `/share/:id` OG-tagged page round trip. `/api/share` accepts `?w=&h=` query params (the canvas's actual pixel dimensions) stored as R2 custom metadata, so `/share/:id`'s `og:image:width/height` reflect the real image instead of a hardcoded guess.

**WhatsApp share gotcha (already fixed, don't reintroduce):** the postcard's share `Blob` is pre-generated in `showResults()` the moment the canvas is built (`window._postcardBlob`), not inside the `shareWhatsApp()` click handler. `navigator.share()` must be called with zero async gap after the user gesture or browsers (notably iOS Safari) silently revoke permission and it falls back to the degraded upload+`wa.me`-link path. If you touch `shareWhatsApp`, keep using the pre-generated blob rather than calling `canvas.toBlob()` at click time.

**Results persistence:** once a player finishes today's quiz, the results/share screen is restored automatically on reload (`restoreResults()`, called from the init IIFE when `local.sessions` has today's date) instead of reverting to the title screen — it only resets via the explicit "🔁 Play Again" button on the results screen itself (`playAgain()`). This requires `results` (the per-question boolean array) and `total` to be stored in the local session record, not just `score`.

**Theme system (`src/game.html` `<style>` block):** the whole visual theme is a two-tier CSS custom property system — a `--p-*` primitives block in `:root` (actual hex values, font stacks: `--p-ivory`, `--p-ink`, `--p-gold`, `--p-vermilion`, `--p-serif` "Zen Old Mincho", `--p-sans` "Zen Kaku Gothic New") feeding the semantic variables (`--text`, `--border`, `--correct`, `--wrong`, `--accent`, etc.) that the rest of the file references. Re-theming means editing the primitives block, not hunting through the file. Canvas-drawn content (the Progress tab's `drawLineChart`) can't read CSS custom properties directly — it resolves them once via `getComputedStyle(document.documentElement)` at the top of the function instead of hardcoding colors, so it stays in sync with the same theme. The Okapia header logo is an inline base64 PNG with a real alpha channel (white background made transparent, ink recolored to `--p-ink`) — not a JPEG with a CSS `invert()` filter (that was the pre-theme approach and doesn't work once the background isn't dark).

**Correct/wrong is never color-only:** both the option-letter badges and the progress-dot recap show a ★ (correct) or ✕ (wrong) symbol alongside the color change, for colorblind accessibility. See `answer()` and `buildMap()`.

**Frontend state:** `game.html` keeps personal progress (scores, streaks, category performance) in `localStorage` under key `okapia_atlas_v1`; nothing is sent server-side except an optional leaderboard score post (name + score + date only). Language preference is a separate `localStorage` key (`carta_lang`); `LANGS` holds the full UI string tables per language.

**Answer disputes** go to GitHub Issues (`GITHUB_REPO` constant in game.html, `.github/ISSUE_TEMPLATE/dispute.md`) with a prebuilt URL linking the question, chosen answer, and Wikipedia source.

## Editing the About/legal copy

`ABOUT_STRINGS` in `worker.js` and the corresponding About-tab strings rendered in `game.html` must stay index-aligned (comment at the top of `ABOUT_STRINGS` calls this out) — changing one without the other breaks translation lookups by index.
